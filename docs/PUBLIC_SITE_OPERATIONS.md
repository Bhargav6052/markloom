# Public website configuration

## HTTPS deployment

After supplying real production values and completing the acceptance checklist:

```sh
docker compose --env-file frontend/.env.local -f compose.yaml -f compose.production.yaml build
docker compose --env-file frontend/.env.local -f compose.yaml -f compose.production.yaml up -d
```

Provide SITE_DOMAIN and ACME_EMAIL through the deployment environment (or a separate ignored env file containing both these values and public build variables). Caddy obtains/renews certificates and redirects port 80 to HTTPS. Keep ports 80/443 reachable and certificate volumes persistent. The web/API containers remain behind the TLS proxy; loopback 8080 is a local diagnostic entry only. HSTS is applied at HTTPS ingress, not faked on localhost. Production readiness blocks missing required operator/domain/bot/server setup.

Validate on the real host: HTTP returns an HTTPS redirect, HTTPS certificate/name/chain are valid, HSTS/security headers appear, no mixed content, `/ready` returns 200 only with required services, unknown public URL returns 404, API/private routes still authorize correctly, and `/sitemap.xml`, `/robots.txt` and social image resolve with appropriate types. Container/Caddy runtime was not available in this workspace; these deployment checks are not recorded as passed.

References used: https://caddyserver.com/docs/automatic-https and https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security.

## Analytics

The server-only `inkloom_website_events` table stores event type, allowlisted public path, consent version and timestamp; random row IDs are event IDs, not visitor identifiers. There is no browser direct access and no tenant/private workspace tracking. The endpoint rejects arbitrary URLs/identity fields and unapproved origins and respects DNT/GPC. Local consent is rechecked before sending. Blocked/unavailable analytics never substitutes fake events.

Use scripts/website-analytics-report.sql through an authorized operator connection. Counts represent events, not unique visitors or customers. No analytics has been collected during this work. Server secret is absent; public config reports analytics unavailable. Configure the server key, opt-in flag, retention process and monitored infrastructure before activation. There is currently no automatic event purge; do not claim one.

## Bot protection

Set TURNSTILE_SITE_KEY on the backend and configure the same widget/allowed hostnames plus verification secret in Supabase Auth CAPTCHA settings. The browser receives only the public site key. Login, signup and recovery pass captchaToken to Supabase; production UI blocks submission if the challenge is unavailable. A frontend widget alone is not server enforcement. Verify direct Auth calls reject missing/invalid tokens after configuring Supabase.

References used: https://supabase.com/docs/guides/auth/auth-captcha and https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/.

## SEO and assets

`VITE_SITE_URL` generates absolute canonical/social URLs and a public-only sitemap. With no domain, source/dev robots and production output intentionally disallow indexing and sitemap is empty. Public pages receive separate built HTML heads; React updates metadata during navigation. Auth/private/error pages stay noindex.

The social PNG/WebP and icons are original local assets generated by scripts/generate-public-assets.py. PNG is used for broad social crawler support; WebP is available for future on-page usage. Decorative WebGL/CSS geometry has no informational alt requirement and is hidden from assistive technology. Original user evidence uploads are not modified to optimize a marketing asset.

`pnpm run build` validates public env variables and scans source/build for secret patterns; it also verifies metadata, assets and image size budgets. A public deploy can require `REQUIRE_PUBLIC_SITE=true`; the production Docker overlay does so. Source maps are disabled. The publishable Supabase key is safe to expose only in combination with the tested RLS/authorization boundaries; server/AI keys remain backend-only.

## Local built-preview authentication

A Vite production bundle is also used by localhost preview; that alone does not make the local development server a production deployment. The public config response now explicitly reports deployment_environment. On a built preview, CAPTCHA is optional only when page and API are both loopback and the API explicitly confirms development with no site key/requirement. A public hostname, production API, remote API, unknown configuration or explicit CAPTCHA still requires protection. This does not disable or alter Supabase Auth's server-side CAPTCHA enforcement. Backend/frontend versions must be updated together; restart the API and refresh the page after changing them.
